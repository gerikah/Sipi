Status meanings: **Locally verified** means repository checks or disposable PGlite/browser fixtures; **Hosted verified** means actual read-only Netlify, Supabase API or trusted SQL inspection; **Blocked** means the release condition is not met or was not tested. A hosted finding can verify a problem without passing its release gate.

## Remaining steps, in order

1. Review the live privacy finding with gerikah. Obtain production authorization before any database, Auth or cron change. Take a protected backup and rehearse its restore into a separate project first; do not use live records as write fixtures.
2. Follow [migration reconciliation](migration-reconciliation.md). Apply only the reviewed additive access repair after approval, then verify anonymous and authenticated direct actor-column reads fail while public and administrator RPCs still work. Do not run `sipi_schema.sql` or blindly push the old migrations.
3. In Supabase Auth settings, disable new user signups; confirm existing approved login still works. Review leaked-password protection availability and enable it where supported. In URL Configuration, verify Site URL `https://sipii.netlify.app` and only required exact redirect destinations. Password login currently uses `detectSessionInUrl: false`; do not add wildcard production redirect origins without a real need. Use a separate project for local/preview Auth URLs.
4. In Netlify project environment settings, confirm `SUPABASE_URL` and `SUPABASE_PUBLISHABLE_KEY` are available to **Builds** in the production context. Preview contexts must point at a separate development project. Keep secret/service-role keys and private CSVs out of Netlify browser builds. Preserve `npm run build`, `dist`, Node 24 and `public/_redirects` (`/* /index.html 200`). No variable rename is needed. Verify the next approved build log without printing values.
5. In an authorized isolated Supabase development project, run real Auth/PostgREST acceptance with owner-managed approved, unapproved and disabled test accounts. Verify login/refresh/logout, an already-open session after membership revocation, draft and related metadata isolation, direct write denial, status RPCs, and raw import/audit/membership privacy. Use synthetic fixtures only; do not put credentials in chat or logs. Run multi-client conflict and lost-response/retry tests there; record results separately from PGlite.
6. Enable `pg_cron` through trusted administration after approval. Review and execute [schedule-import-retention.sql](../supabase/operations/schedule-import-retention.sql): one daily `sipi-import-retention` job at 19:00 UTC (03:00 Manila), owned by postgres. Check the next scheduled run succeeds using `cron.job_run_details`; inspect only aggregate before/after retention data. No immediate live cleanup is authorized here.
7. Confirm the source's ambiguous name boundaries with an authorized reviewer. Record the review separately; do not automatically repair existing people lists or infer student identifiers.
8. After approved fixes, rerun hosted read checks/advisors and authenticated acceptance. Schedule an explicitly authorized frontend deployment, then repeat direct route refresh, both themes/mobile, and browser asset checks against that exact deployment. Preserve prior deploy ID for rollback. Phase 6 is complete only when these gates and recovery evidence are recorded.

## Current Supabase advisor findings

- Security: five private tables with RLS and no policies are deliberate deny-by-default with revoked grants. `list_imports` is an authenticated security-definer RPC with active membership and ownership checks; local tests cover denial. The platform `public.rls_auto_enable()` has browser execute grants; the prepared repair revokes them while preserving event-trigger execution. Leaked-password protection remains disabled. These explanations do not clear dashboard warnings automatically.
- Performance: eight unindexed foreign keys (`audit_logs.actor_id/batch_id`, `import_batches.source_id/uploaded_by`, `import_rows.thesis_id`, `theses.academic_year_id/created_by/updated_by`); seven currently unused indexes; eleven multiple permissive SELECT-policy notices for authenticated access. No index or RLS policy was removed. Public-or-admin policies are intentional. Validate query plans and index write cost in development before a separate tuning migration; small current data and an unused-index notice do not establish that an index is unnecessary.

Read-only evidence is retained under ignored `.local/release/`; private source files and credentials are not documentation attachments. Counts are a 23 October snapshot, not permanent product copy.
